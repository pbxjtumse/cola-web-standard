# 1.2.0 优化审查报告

## 一、审查目标

本次审查不是继续增加一期能力，而是检查 1.1.0 在真实基础组件场景下是否存在：

- API 重载持续增长；
- 配置语义不明确；
- 扩展点违反契约；
- 异常规则结果不稳定；
- 服务异常对象造成死循环；
- 随机退避难以测试；
- 同名策略被无感覆盖；
- 取消、标识和上下文没有统一入口；
- 指标监听器重复创建对象；
- 注释无法自动检查。

最终结论：1.1.0 的总体方向正确，但还不适合作为稳定 API 冻结版本。1.2.0 修复了本次识别出的核心问题，仍不建议立即声明 API 永久稳定，应先完成真实消息发送和事务模板集成验证。

## 二、问题与优化对应关系

| 编号 | 1.1.0 问题 | 风险 | 1.2.0 处理 |
|---|---|---|---|
| O-01 | 执行入口依赖不断增加重载 | 每增加取消、属性或业务 ID 都要扩展接口 | 新增 `RetryExecution<T>` 请求对象 |
| O-02 | 没有调用方取消协议 | 已经不需要的请求仍继续重试 | 新增 `RetryCancellationToken` |
| O-03 | 重试 ID 只能由核心内部生成 | 无法与消息 ID、请求 ID 或任务 ID 对齐 | 新增 `RetryIdGenerator` 和自定义 `retryId` |
| O-04 | 同一动作规则匹配依赖声明顺序 | `Exception` 可能抢先覆盖 `IOException` | 使用继承距离选择最具体规则 |
| O-05 | cause 遍历缺少环检测 | 自定义异常 cause 环可能无限循环 | 身份去重加 `maxCauseDepth` |
| O-06 | 同一异常可同时出现在多个动作 | 行为取决于内部动作优先级，配置难发现 | 构建阶段拒绝精确类型冲突 |
| O-07 | 自定义分类器和声明式规则可混用 | 调用者不知道哪套规则真正生效 | 构建阶段禁止混用 |
| O-08 | 分类器可能把失败判为成功 | 真实异常被错误吞掉 | 执行器校验决策与尝试一致性 |
| O-09 | 随机抖动使用固定全局随机源 | 单元测试无法稳定复现 | 允许注入 `RandomGenerator` |
| O-10 | `register` 静默覆盖 | 配置重复或 Bean 重复时行为悄悄变化 | `register` 拒绝重复，`replace` 显式覆盖 |
| O-11 | 配置列表无法区分缺失与空列表 | 子策略无法明确清空父规则 | 列表使用三态语义：null/空/非空 |
| O-12 | 循环继承错误上下文不足 | 多级配置故障难定位 | 输出完整继承路径并使用 finally 清理 |
| O-13 | 扩展基础设施无法通过 Spring 覆盖 | 测试或平台集成必须重写自动配置 | 暴露 Clock、Sleeper、ID Generator Bean |
| O-14 | 指标监听器重复查找/创建计量器 | 高频事件下产生不必要开销 | 缓存计量器并补 active/backoff 指标 |
| O-15 | 机械逐行注释遮挡业务语义 | 代码体积膨胀，维护者无法快速定位关键说明 | 删除生成脚本，改用业务语义注释与风格验证 |

## 三、未采用的优化

### 1. 没有把 `attemptTimeout` 塞入同步核心

同步方法无法被 Java 安全强杀。仅在方法返回后判断超时，会制造“看似超时、物理任务仍执行”的错误承诺。该能力必须和并行组件的受管执行载体、取消策略和遗留任务治理一起设计。

### 2. 没有增加注解式重试

注解会隐藏实际尝试次数、事务边界、幂等要求和代理限制。应等显式 API 经过消息、事务和 HTTP 集成验证后，再在独立 Spring 集成层提供语法糖。

### 3. 没有把 RetryBudget 放入一期

预算需要按下游资源划分，并与治理组件的限流、熔断和指标聚合对齐。单纯增加一个全局令牌桶会给出错误安全感。

### 4. 没有引入持久化重试表

本地同步重试和跨进程可恢复重试是两个不同系统。后者涉及任务序列化、租约、抢占、心跳、幂等、版本和人工重放，应与任务组件共同设计。

### 5. 没有直接依赖开源重试库

核心组件需要和现有消息、事务、并行、治理、幂等组件形成统一模型。直接以第三方库对象作为公共 API 会把外部库的生命周期和升级风险暴露给所有组件。

## 四、仍需继续观察的问题

1. `RetryPolicy` Builder 的声明式异常规则适合通用场景，但协议集成可能需要更完整的组合分类器。
2. 当前动作优先级固定为 `ABORT > STOP > RETRY`。这是安全优先原则，但需要在真实集成中验证是否足够直观。
3. 返回结果规则按声明顺序匹配，因为 Predicate 不存在可靠的“特异性”比较方式；同一结果命中多个规则时由调用方负责顺序。
4. `operationName` 和 `policyName` 会进入指标标签，必须限制为有限集合。
5. 协作式取消不能终止已经运行的同步业务方法。
6. 当前事件监听器同步执行，虽然异常隔离，但慢监听器仍可能增加总耗时；二期需要评估异步事件投递或观测缓冲。
7. Spring 策略动态刷新尚未实现；未来只能原子替换不可变策略，不能修改正在执行的快照。
8. 1.3.0 已删除机械逐行注释；后续继续依赖准确的 Javadoc、关键流程注释、测试和设计文档表达语义。

## 五、建议的下一步

在进入二期之前，建议先使用 1.2.0 完成两项真实集成验证：

1. 消息组件发送路径：验证 Provider 内部重试与外层逻辑重试不会倍增失控。
2. 事务模板：验证重试包裹完整事务边界，数据库死锁异常可以稳定分类。

这两项验证后再决定哪些 API 可以冻结，哪些应继续收敛。
