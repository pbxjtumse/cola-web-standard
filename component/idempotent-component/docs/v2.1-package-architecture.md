# Idempotent Component V2.1 分包设计

> 基线：用户当前 `idempotent-component.zip`（V2）。  
> 目标：先完整落地此前讨论的 V1.3 API / StateMachine / ResultPolicy / PolicyRegistry / Capabilities，再按真实职责分包。  
> 原则：分包不改变幂等正确性，不为了“目录漂亮”制造大量 Manager/Service/Handler。

---

## 1. 为什么这次先增强再分包

当前 V2 的核心正确性其实已经成立：

```text
Idempotency Key
  + Repository 原子状态转换
  + PROCESSING / SUCCESS / FAILED
  + ownerToken / version
  + optional DistributedLock 短临界区
  + Tx-A / Tx-B / Tx-C
  + Reliable Recovery CAS
```

真正需要解决的是两个结构问题：

1. API 中 Request、Policy、Context、Result、Recovery 等概念混在同一层级；
2. Core 中 Executor、Policy Registry、Repository Registry、Owner、Failure、StateMachine 等职责平铺。

如果只分包、随后再引入 ResultPolicy/StateMachine/PolicyRegistry，会再次移动公共类型。因此本版本先稳定能力边界，再一次性分包。

### 2.1 `execution`

只描述“如何调用幂等组件”。

不应该包含 Repository、Provider 或具体事务实现。

### 2.2 `request`

只描述“这一次逻辑请求是谁”：

```text
key
requestHash
routeKey
policyName / inline policy
```

不再把一整套生命周期配置塞进 Request。

### 2.3 `policy`

描述“一类业务平时怎么做幂等”，包括：

```text
WINDOWED / DURABLE
namespace
repositoryName
processingTimeout
idempotencyWindow
recordRetentionTtl
RecoveryPolicy
LockOptions
```

### 2.4 `result`

只解决：

> 历史已经 SUCCESS 时，本次重复请求拿到什么？

它不负责抢锁、状态转换或 Recovery。

### 2.5 `repository.acquire / recovery / write`

虽然都操作同一条幂等记录，但三个协议完全不同：

```text
acquire
  普通请求争夺/判断当前 generation

recovery
  Reliable Task 基于 expectedOwner/version 二次 CAS 接管

write
  当前 owner/version 完成 SUCCESS 或 FAILED
```

把三组模型分包可以避免 Repository 包继续膨胀。

### 3.1 为什么没有继续拆 `DefaultIdempotencyExecutor`

Executor 是主流程编排器，应该让阅读代码的人能在一个地方看到：

```text
prepare
→ lock
→ tryAcquire
→ state machine
→ execute/replay/return
→ transaction
→ final CAS
```

如果继续人为拆成：

```text
AcquireManager
CompletionManager
ResultManager
RecoveryManager
TransactionManager
```

反而会让核心流程散掉。

所以这次分包只拆“稳定独立职责”，不拆“同一编排过程”。

## 4. Provider 包结构

### JDBC

```text
provider.jdbc
├── execution
│   ├── JdbcExecutionManager
│   ├── DataSourceJdbcExecutionManager
│   └── JdbcWork
└── repository
    └── JdbcIdempotencyRepository
```

`execution` 负责 Connection/事务参与；`repository` 负责幂等状态 SQL。

### Redis

```text
provider.redis
├── key
│   └── RedisIdempotencyKeyBuilder
└── repository
    └── RedisIdempotencyRepository
```

Lua 保持在 resources 中，Repository 负责脚本调用和结果映射。

---

## 5. Transaction Integration

```text
integration.transaction
├── coordinator
│   └── TransactionTemplateIdempotencyTransactionCoordinator
└── jdbc
    └── SpringTransactionJdbcExecutionManager
```

二者职责完全不同：

```text
coordinator
  Tx-B REQUIRED：Business + ResultPolicy.capture + markSuccess

jdbc
  Tx-A / Tx-C REQUIRES_NEW + Tx-B transaction-bound Connection
```

## 6. Starter

```text
starter
├── autoconfigure
├── properties
├── result
├── hash
└── observation
```

Starter 只负责组装，不承载领域状态机。

## 7. 本版本公共 API 的稳定边界

业务最常面对的类型应控制在：

```text
IdempotencyExecutor
IdempotencyRequest
IdempotencyPolicy / policyName
IdempotencyResult<T>
IdempotencyResultPolicy<T>
IdempotencyRecoveryRequest
```

而下面这些虽然公开，是 Provider / Reliable Task 扩展协议，不是普通业务每天直接使用的对象：

```text
IdempotencyRepository
AcquireRequest/Result
RecoveryAcquireRequest/Result
SuccessRequest/FailureRequest
```

---

## 8. 兼容策略

当前保留：

```text
IdempotencyMode.SHORT_TERM   @Deprecated → canonical WINDOWED
IdempotencyOptions           @Deprecated → IdempotencyPolicy
IdempotencyResultCodec       @Deprecated → ResultPolicy<T>
```

这意味着旧设计不会突然消失，但新业务应直接进入新 API。

---

## 9. 最终依赖方向

```text
Business
   ↓
idempotent-api
   ↓
idempotent-core
   ↓
Repository SPI
   ├── JDBC Provider
   └── Redis Provider

idempotent-core
   ├── optional distributed-lock-api
   └── transaction SPI
          ↑
          └── idempotent-integration-transaction
                    ↓
             transaction-component
```

核心原则：Provider/Integration 可以依赖 API/Core，但 API 不反向依赖 Spring、Redis、JDBC 或 transaction-component。
