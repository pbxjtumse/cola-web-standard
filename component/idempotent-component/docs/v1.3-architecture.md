# V1.3 架构与执行流程

## 1. 先纠正一个容易误解的图

下面这种画法：

```text
Recovery
   ↓
State Machine
   ↓
Repository CAS
   ↓
┌─────────────┴─────────────┐
Lock                    Transaction
```

容易让人误以为：

1. State Machine 先做决定，Repository 再 CAS；
2. Lock 与 Transaction 是 Repository CAS 之后的两个并列替代方案。

V1.3 **不是这个结构**。

准确结构是：

```text
Request
  ↓
Policy Resolution
  ↓
Repository Resolution
  ↓
┌─────────────────────────────────────────┐
│ optional short DistributedLock          │
│                                         │
│   Repository.tryAcquire / tryRecover    │
│   UNIQUE / row-lock / Lua / CAS         │
└─────────────────────────────────────────┘
  ↓
State Machine interprets atomic result
  ├─ RETURN / REPLAY
  └─ EXECUTE
        ↓
      Business
        +
      ResultPolicy.capture
        +
      Repository.markSuccess CAS
        ↑
        │
   optional Transaction Integration
   (Tx-B REQUIRED, when supported)
```

因此三者职责完全不同：

```text
Lock
= 降低抢占阶段的热点竞争

Repository CAS/Lua
= 正确性核心，真正决定 generation owner

State Machine
= 把 Repository 原子结果翻译成稳定执行动作

Transaction
= owner 已经确定以后，把 Business + final SUCCESS 绑进同一本地事务
```

## 2. 正常 execute()

### 2.1 第一次请求

```text
A
│
├─ key = order:req-1001
├─ policy = order-create
└─ resultPolicy = REFERENCE
        │
        ▼
PolicyRegistry.resolve()
        │
        ▼
RepositoryRegistry.resolve(capabilities)
        │
        ▼
optional short lock
        │
        ▼
Repository.tryAcquire()
        │
        ├ JDBC: UNIQUE + short Tx-A + SELECT FOR UPDATE
        └ Redis: Lua
        │
        ▼
ACQUIRED(owner=A, version=1)
        │
        ▼
StateMachine -> EXECUTE
        │
        ▼
Business + ResultPolicy.capture + markSuccess
        │
        ▼
SUCCESS
```

### 2.2 重复请求，第一次已经成功

```text
B same key
   ↓
tryAcquire()
   ↓
Repository atomic result = SUCCESS
   ↓
StateMachine = REPLAY
   ↓
callback 不执行
   ↓
ResultPolicy.replay(...)
   ↓
REPLAYED
```

### 2.3 重复请求，第一次仍然执行中

```text
B
 ↓
tryAcquire()
 ↓
PROCESSING_ACTIVE
 ↓
StateMachine = RETURN
 ↓
PROCESSING
```

B 不会自动启动第二次业务。

## 3. 为什么 State Machine 在 CAS 之后

不能做：

```text
SELECT status
  ↓
Java 判断可执行
  ↓
UPDATE PROCESSING
```

因为 A/B 可能同时 SELECT 到同一个旧状态。

V1.3 的 Repository 接口返回的是**原子状态转换的结果**：

```text
JDBC:
UNIQUE / SELECT FOR UPDATE / conditional UPDATE

Redis:
Lua script
```

例如：

```text
A tryAcquire ─┐
              ├─ Repository serialization/CAS ─→ A ACQUIRED
B tryAcquire ─┘                              └→ B PROCESSING_ACTIVE
```

然后 State Machine 才翻译：

```text
ACQUIRED          -> EXECUTE
PROCESSING_ACTIVE -> RETURN PROCESSING
SUCCESS           -> REPLAY
KEY_CONFLICT      -> RETURN KEY_CONFLICT
```

所以 `StateMachine` 是“领域解释器”，不是并发互斥器。

## 4. Recovery 完整流程

Recovery 解决的是：

```text
A 已经拿到 generation
但是 A 超时、宕机、或以 retryable failure 结束
```

它不是普通重试器。

### 4.1 扫描

外部 Reliable Task：

```text
findCandidates(policyName, query)
        ↓
candidate:
 namespace
 key
 ownerToken=A
 version=10
 reason=PROCESSING_TIMEOUT
```

扫描只产生候选，不拥有执行权。

### 4.2 真正接管

任务执行器随后调用：

```text
recover(
  expectedOwner=A,
  expectedVersion=10
)
```

Repository 原子验证：

```text
记录仍存在
AND recovery policy 允许
AND owner仍是 A
AND version仍是 10
AND requestHash / routeKey 不冲突
AND:
    PROCESSING 已超时
    或 FAILED retryable 且允许恢复
```

只有全部满足才：

```text
owner = B
version = 11
status = PROCESSING
processingExpireAt = now + processingTimeout
```

然后返回：

```text
RECOVERY_ACQUIRED
```

State Machine 才允许：

```text
EXECUTE
```

### 4.3 为什么一定要 expectedOwner + expectedVersion

扫描与执行之间可能有时间差：

```text
T1 scanner 看到 A/version10 超时
T2 C 已经先接管成 version11
T3 旧扫描任务才开始执行
```

如果没有 CAS：

```text
旧扫描任务又会错误接管
```

有 expectedOwner/version：

```text
expected=A/10
current=C/11
    ↓
STALE_CANDIDATE
```

任务安全结束，不执行业务。

## 5. PROCESSING_EXPIRED 为什么普通 execute() 不直接接管

因为普通请求看到“当前执行权租约过期”并不代表：

```text
旧线程一定已经死了
```

旧线程可能只是：

```text
Full GC
CPU 长时间调度不到
网络停顿
线程阻塞
```

因此 V1.3 把：

```text
普通请求去重
```

和：

```text
异常 generation 恢复
```

明确分开。

默认行为：

```text
execute()
  PROCESSING_EXPIRED
  -> 返回状态
  -> 不自动变更 owner/version
```

只有明确启用：

```text
RecoveryPolicy.EXTERNAL_TASK
```

的可靠任务路径才能调用 `recover()`。

## 6. Lock 在哪里

Lock 只包：

```text
tryAcquire / tryRecover
```

也就是很短的状态抢占临界区：

```text
lock
 ↓
Repository CAS/Lua
 ↓
unlock
 ↓
Business
```

不包：

```text
Business
HTTP
RPC
长 SQL
结果等待
```

原因：

1. Repository 本身已经具备正确性；
2. 长时间持有分布式锁会扩大租约过期/续期/GC 风险；
3. 锁的价值主要是减少热点 key 下的大量 DB/Lua 冲突；
4. lock 获取失败时，若配置 `fallbackToStateOnFailure=true`，仍可退回 Repository CAS。

所以 Lock 是：

```text
contention reduction
```

不是：

```text
correctness authority
```

---

## 7. Transaction 在哪里

Transaction 只在 State Machine 已经授予 `EXECUTE` 后生效。

JDBC Transaction-aware Repository：

```text
Tx-A REQUIRES_NEW
  tryAcquire/tryRecover
  PROCESSING
COMMIT
    ↓
State Machine -> EXECUTE
    ↓
Tx-B REQUIRED
  Business
  ResultPolicy.capture
  markSuccess CAS
END
```

如果业务失败：

```text
Tx-B rollback
   ↓
Tx-C REQUIRES_NEW
  markFailed
COMMIT
```

因此：

```text
Lock = 抢执行权之前/期间的并发优化
Transaction = 已拥有执行权以后，业务与最终状态的原子性
```

两者不在同一层。

---

## 8. markSuccess CAS 为什么还必须保留

即使 Tx-B 存在，也不能：

```sql
UPDATE idempotency
SET status='SUCCESS'
WHERE key=?
```

必须：

```sql
WHERE key=?
  AND status='PROCESSING'
  AND owner_token=?
  AND version=?
```

因为可能：

```text
A version10 执行业务期间超时
B recover -> version11
A 恢复
```

A 在 Tx-B 最后 `markSuccess(A,10)`：

```text
0 rows
```

Core 抛内部 `CompletionRejectedException`，让：

```text
A 的 Business SQL + SUCCESS
```

整个 Tx-B 回滚。

这才是旧 generation 隔离。

---

## 9. ResultPolicy 在哪里

ResultPolicy 只作用在两个点：

```text
第一次真实执行：
Business -> T
         -> ResultPolicy.capture(T)
         -> result_payload

重复 SUCCESS：
result_payload
         -> ResultPolicy.replay(...)
         -> T
```

它不参与：

```text
是否 ACQUIRED
PROCESSING 是否过期
谁能 recover
owner/version CAS
分布式锁
事务传播
```

因此它属于“成功结果的重复响应策略”，不是幂等唯一性策略。

## 10. 最终职责表

| 能力 | 回答的问题 |
|---|---|
| IdempotencyKey | 哪些请求被认为是同一个逻辑动作 |
| requestHash | 同 key 是否被错误用于不同请求内容 |
| Policy | 这类幂等请求的生命周期/恢复/Repository/锁策略是什么 |
| Repository CAS/Lua | 当前 generation 到底属于谁 |
| ownerToken + version | 旧执行者是否还有完成资格 |
| State Machine | Repository 原子结果在领域上应该 EXECUTE/REPLAY/RETURN 什么 |
| DistributedLock | 是否要降低热点状态抢占竞争 |
| Transaction | Business + SUCCESS 是否能在同一本地事务提交/回滚 |
| ResultPolicy | 重复 SUCCESS 请求应该返回什么 |
| RecoveryPolicy | 哪些异常 generation 可以由可靠任务接管 |
| Reliable Task | 什么时候扫描、调度和执行 recovery |
