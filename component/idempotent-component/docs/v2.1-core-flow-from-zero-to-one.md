# Idempotent Component V2.1：从零到一理解完整幂等流程

> 本文严格按照当前 V2.1 代码主链解释，不把“未来可能做的能力”混入现状。  
> 建议阅读顺序：先理解逻辑请求 → generation → Repository 原子判断 → StateMachine → Tx-A/B/C → ResultPolicy → Recovery。

---

# 1. 幂等到底解决什么问题

幂等不是“保证请求只发送一次”。分布式系统里做不到这一点。

真实世界一定会出现：

```text
HTTP 超时重试
MQ 重复投递
定时任务重复触发
用户按钮连点
网关重试
服务重启
旧线程 Full GC 后恢复
多个 Pod 同时处理同一个业务键
```

例如第一次创建订单：

```text
客户端
  ↓ requestId=REQ-1001
服务
  ↓
创建 ORDER-888
  ↓
数据库 COMMIT 成功
  ↓
返回 HTTP 200 时网络断开
```

客户端只看见 Timeout。它不知道订单到底有没有创建，于是再次发送：

```text
requestId=REQ-1001
```

没有幂等时可能再次创建 ORDER-889。

因此组件真正保证的是：

> **同一个逻辑请求无论被提交多少次，都不能产生多个合法业务效果。**

注意，这个定义没有要求“只能存在一个线程”。

我们接受 A、B 线程甚至 A、B 节点同时存在，但要保证只有一个 **合法 execution generation**。

---

# 2. 第一步：如何识别“同一个逻辑请求”

## 2.1 Idempotency Key

`IdempotencyRequest.key` 是逻辑请求身份证。

例如：

```text
order:create:REQ-1001
payment:PAY-20260817-001
message:messageId-888
```

第一次、网络重试、MQ 重投必须携带相同 key。

JDBC 最终通过：

```text
UNIQUE(namespace, idempotency_key)
```

保证同一逻辑范围内只有一条当前幂等记录。

## 2.2 namespace

namespace 用于业务隔离：

```text
namespace=order-create, key=1001
namespace=refund,       key=1001
```

它们是两个不同幂等请求。

所以真正唯一范围是：

```text
(namespace, key)
```

## 2.3 requestHash

只有 key 仍不够。

第一次：

```text
key=PAY-001
amount=100
```

第二次错误复用了同一个 key：

```text
key=PAY-001
amount=500
```

如果只看 key，第二次会被误认为第一次的重复请求。

所以保存 requestHash：

```text
100 元请求 → hash AAA
500 元请求 → hash BBB
```

同 key 但 hash 不一致时 Repository 返回：

```text
KEY_CONFLICT
```

因此：

```text
key         = 逻辑身份
requestHash = 对身份对应业务内容的二次校验
```

## 2.4 routeKey

routeKey 不参与“是不是同一个请求”的身份判断。

它负责业务路由，例如：

```text
merchant-1001 → DB shard 01
merchant-2001 → DB shard 02
```

Reliable Recovery 必须把扫描时保存的 routeKey 原样带回，保证恢复仍回到同一业务分片。

# 3. Request 与 Policy 为什么必须分开

V2.1 把两个问题彻底拆开。

## Request 回答

> 这一次请求是谁？

```text
key
requestHash
routeKey
policyName / inline policy
```

## Policy 回答

> 这种业务通常应该怎样做幂等？

```text
WINDOWED / DURABLE
namespace
Repository
processingTimeout
idempotencyWindow
recordRetentionTtl
RecoveryPolicy
LockOptions
```

业务可以只写：

```java
IdempotencyRequest request = IdempotencyRequest.builder()
        .key(requestId)
        .requestHash(hash)
        .routeKey(merchantId)
        .policyName("order-create")
        .build();
```

而 `order-create` 在 Starter 配置中统一定义。

这样不会在几十个业务方法中复制同一堆 Options。

# 4. WINDOWED 与 DURABLE

## 4.1 WINDOWED

正式名称是 `WINDOWED`，历史 `SHORT_TERM` 只保留 deprecated 兼容。

它表达：

> 相同 key 只在一个有限时间窗口内被认为是同一次逻辑请求。

例如：

```text
idempotencyWindow = 10min
```

10:00 首次执行；10:03 同 key 仍然重复；10:11 窗口已经结束，可以开启新的 generation。

典型场景：

```text
按钮连点
短时间 HTTP 重复提交
短周期任务去重
```

Redis 是默认 Provider，但 WINDOWED 是领域语义，不等于 Redis。

## 4.2 DURABLE

DURABLE 表达：

> 这个幂等事实是长期业务事实，不能因为一个短 TTL 到期就忘记。

例如支付：

```text
paymentRequestId=PAY-001
```

今天、明天、一个月后再次收到 PAY-001，都不能重新产生第二次扣款。

典型场景：

```text
订单
支付
退款
结算
重要消息消费
```

默认使用 JDBC。

---

# 5. 三个时间为什么必须区分

这是窗口幂等最容易混淆的地方。

假设：

```text
processingTimeout  = 30s
idempotencyWindow  = 10min
recordRetentionTtl = 1h
```

## processingTimeout

描述当前 generation 的执行权租约。

```text
A 在 10:00:00 获得 PROCESSING
processingExpireAt=10:00:30
```

10:00:31 以后只能说明：

> A 的 execution lease 过期。

它不代表 A 的 Java 线程已经死亡。

## idempotencyWindow

描述 WINDOWED 下，同 key 多久仍算同一次逻辑请求。

10:10 以后可以进入新 generation。

## recordRetentionTtl

描述窗口结束后旧物理记录额外保留多久用于排障/观测。

所以：

```text
10:00      首次执行
10:00:30   execution lease 到期
10:10      幂等语义窗口结束
11:10      旧物理记录才允许清理
```

语义窗口结束不等于物理记录立刻删除。

---

# 6. 幂等真正的核心：generation

第一次请求 A 成功抢占：

```text
status     = PROCESSING
ownerToken = A
version    = 1
```

它表示：

> 当前第 1 代 execution generation 属于 A。

以后 A 异常，B 被 Reliable Recovery 接管：

```text
status     = PROCESSING
ownerToken = B
version    = 2
```

此时 A/1 就是 stale generation。

## ownerToken

回答：

> 当前是谁？

## version

回答：

> 当前是第几代？

两者组合是 execution generation 的身份证。

这比仅仅保存 `PROCESSING=true` 强得多，因为它能够识别旧线程恢复。

---

# 7. 持久状态为什么只有三个

`IdempotencyStatus` 只有：

```text
PROCESSING
SUCCESS
FAILED
```

这是数据库/Redis 真正保存的业务生命周期状态。

而：

```text
PROCESSING_ACTIVE
PROCESSING_EXPIRED
FAILED_RETRYABLE
FAILED_FINAL
```

是 Repository 根据记录字段和当前时间计算出来的“判定结果”，不是第四、第五种持久状态。

例如数据库一直保存：

```text
status=PROCESSING
processingExpireAt=10:00:30
```

10:00:20 判断为 PROCESSING_ACTIVE；10:00:31 判断为 PROCESSING_EXPIRED。

因此整个组件存在三层状态语义：

```text
持久状态：IdempotencyStatus
        ↓
Repository 判定：AcquireStatus / RecoveryStatus
        ↓
本次 API 结果：IdempotencyResultStatus
```

千万不要把 `REPLAYED` 当成数据库状态。数据库仍然是 SUCCESS；REPLAYED 只是“本次调用没有执行 callback”。

# 8. execute() 主流程总览

当前主 API：

```java
idempotencyExecutor.execute(request, callback)
```

默认 ResultPolicy 为 NONE。

需要结果回放时：

```java
idempotencyExecutor.execute(request, resultPolicy, callback)
```

内部主线：

```text
Request
  ↓
Policy Resolution
  ↓
Repository Resolution + Capabilities
  ↓
生成 ownerToken
  ↓
optional short DistributedLock
  ↓
Repository.tryAcquire()
  ↓
StateMachine
  ├─ EXECUTE
  ├─ REPLAY
  └─ RETURN
```

---

# 9. Policy Resolution

`DefaultIdempotencyPolicyRegistry` 固定优先级：

```text
inline policy
  > legacy IdempotencyOptions
  > policyName
  > default policy
```

进入 Core 后解析成稳定 `IdempotencyPolicy`。

随后 `IdempotencyExecutionDefinition<T>` 冻结：

```text
Policy
Repository
ResultPolicy<T>
```

之后主流程不再到处重新读取可选配置。

---

# 10. Repository Resolution 与 Capabilities

Repository 不再靠名称猜能力。

Provider 显式声明：

```text
windowedSupported
durableSupported
resultPayloadSupported
businessTransactionParticipationSupported
recoveryQuerySupported
```

例如当前 Redis 主要承载 WINDOWED；JDBC 支持 DURABLE，并可在 transaction-aware JdbcExecutionManager 下参加 Business 事务。

因此 Core 做的是：

```text
Policy 需要什么
        ↓
Repository.capabilities() 是否支持
```

而不是：

```text
if providerName == redis ...
```

---

# 11. optional DistributedLock 到底在哪里

锁只包“状态抢占短临界区”：

```text
DistributedLock
   ↓
Repository.tryAcquire()
   ↓
unlock
   ↓
Business
```

Recovery 同样：

```text
DistributedLock
   ↓
Repository.tryRecover()
   ↓
unlock
```

它绝不包完整业务。

## 为什么？

因为幂等正确性不能建立在“Redis 锁永不失效”这个假设上。

锁会：

```text
租约过期
GC 暂停
网络分区
Provider 异常
旧线程恢复
```

所以锁只负责 contention reduction：减少热点 key 同时冲击 DB/Lua。

配置允许 fallback 时，锁不可用仍直接进入 Repository 原子状态机，正确性仍成立。

---

# 12. Repository.tryAcquire() 才真正决定谁能执行

## JDBC 第一次请求

首先尝试：

```sql
INSERT ... status='PROCESSING', owner=A, version=1
```

依靠：

```text
UNIQUE(namespace, idempotency_key)
```

A、B 并发第一次进入时只能一个 INSERT 成功。

## Duplicate 以后

另一个线程进入短事务：

```text
SELECT ... FOR UPDATE
  ↓
读取当前记录
  ↓
判断 requestHash / routeKey / status / window / processing lease
  ↓
必要时在同一短事务中完成状态更新
```

## Redis

同样的逻辑由 Lua 一次完成：

```text
读取
判断
必要修改
```

避免 GET → Java 判断 → SET 的 Check-Then-Act 竞态。

因此真正的正确性边界是 Repository 原子操作。

```text
ACQUIRED
SUCCESS
PROCESSING_ACTIVE
PROCESSING_EXPIRED
FAILED_RETRYABLE
FAILED_FINAL
KEY_CONFLICT
PROVIDER_ERROR
```

这时才交给 `IdempotencyStateMachine`。

# 14. StateMachine 为什么存在

以前 Executor 里到处 switch/if：

```text
SUCCESS 怎么办？
PROCESSING 怎么办？
Recovery SUCCESS 又怎么办？
```

现在 StateMachine 专门负责：

> Repository 已经给出了一个原子事实，Core 下一步做 EXECUTE、REPLAY 还是 RETURN？

映射例如：

```text
ACQUIRED           → EXECUTE
SUCCESS            → REPLAY
PROCESSING_ACTIVE  → RETURN PROCESSING
PROCESSING_EXPIRED → RETURN PROCESSING_EXPIRED
FAILED_RETRYABLE   → RETURN PREVIOUS_FAILED_RETRYABLE
KEY_CONFLICT       → RETURN KEY_CONFLICT
```

必须注意：

> StateMachine 不负责并发正确性。

它不做 DB 查询、不做 Lua、不做 CAS。

正确顺序是：

```text
Repository Atomic Operation
        ↓
StateMachine Pure Decision
```

不是反过来。

---

# 15. 为什么普通 execute() 不自动接管 PROCESSING_EXPIRED

A 的 processing lease 超时，不等于 A 已经死亡。

可能只是：

```text
Full GC
STW
线程长期调度不到
网络卡顿
```

如果普通 B 一看过期就接管：

```text
A 恢复
+
B 新执行
```

两者会真正重叠。

所以普通 execute() 只返回：

```text
PROCESSING_EXPIRED
```

不自动恢复。

故障恢复必须通过显式 Reliable Recovery 流程。

---

# 16. ACQUIRED 后发生什么

只有 StateMachine 给出 EXECUTE，Core 才创建 `IdempotencyContext` 并调用 callback。

Context 主要暴露：

```text
namespace
key
routeKey
ownerToken
generationVersion
mode
processingExpireAt
recoveryExecution
```

注意这里的 version 是幂等 generation 版本，不应和 distributed-lock fencing token 强行等同。

---

# 17. Tx-A：为什么 PROCESSING 必须先独立提交

JDBC `tryAcquire/tryRecover` 走 `inNewTransaction()`。

有 transaction-component 时对应：

```text
Tx-A REQUIRES_NEW
```

流程：

```text
BEGIN
  ↓
INSERT / SELECT FOR UPDATE
  ↓
PROCESSING + owner/version
  ↓
COMMIT
```

然后短 DistributedLock 已经释放，才真正跑 Business。

## 为什么不能把 PROCESSING + Business + SUCCESS 放一个长事务？

如果 Business 运行 30 秒：

```text
BEGIN
INSERT PROCESSING
Business 30s
SUCCESS
COMMIT
```

这 30 秒里 PROCESSING 尚未提交，其他节点可能看不到它，或者被唯一键/行锁阻塞。

PROCESSING 的意义就是让其他请求尽快看到“已经有人在处理”，所以它必须先提交。

---

# 18. Tx-B：Transaction Integration 真正解决什么

执行权已经由 Repository 决定，事务模板不负责“谁能执行”。

Transaction Integration 解决：

> 同一数据库资源中，Business 与最终 SUCCESS 能不能原子提交？

Tx-B 固定：

```text
REQUIRED
  Business callback
  + ResultPolicy.capture
  + markSuccess(owner, version)
```

如果调用方已有外层事务，REQUIRED 加入外层事务；没有时才建立事务。

## 为什么不是 REQUIRES_NEW？

如果幂等业务独立提交 SUCCESS，之后调用方外层事务又回滚，会产生：

```text
幂等表 SUCCESS
业务整体却失败
```

所以 Tx-B 必须跟随业务真实本地事务边界。

---

# 19. JDBC 为什么必须复用 transaction-bound Connection

只创建 TransactionExecutor 还不够。

如果业务使用 Connection-A，但 `markSuccess()` 自己 `dataSource.getConnection()` 得到 Connection-B：

```text
Business       → Tx/Connection A
markSuccess    → Connection B
```

表面看有事务，实际上仍然是两个提交点。

因此 `SpringTransactionJdbcExecutionManager` 使用 `DataSourceUtils`：

```text
Business SQL
+
markSuccess SQL
```

真正复用同一 transaction-bound Connection。

并且如果当前事务并未绑定幂等 DataSource，会 fail-fast，而不是假装“应该在同一事务”。

---

# 20. final state 为什么还必须 owner/version CAS

进入 Business 的线程不代表永远拥有完成权。

场景：

```text
A owner=A version=10
  ↓
A 卡住
  ↓
Reliable Recovery B 接管
owner=B version=11
  ↓
A 恢复
```

A 最后调用：

```sql
UPDATE ...
SET status='SUCCESS'
WHERE status='PROCESSING'
  AND owner_token='A'
  AND version=10;
```

数据库当前已经 B/11，因此更新 0 行。

A 被判定为 stale owner。

同样，旧 A 连写 FAILED 都必须带 owner/version 条件，不能覆盖新 generation。

---

# 21. 为什么 CAS 失败还必须让 Tx-B rollback

假设 A 已经在 Tx-B 中执行了一条业务 SQL：

```text
UPDATE account ...
```

随后 `markSuccess(A,10)` 因为 B/11 已接管而更新 0 行。

如果 Executor 只是返回 `OWNERSHIP_LOST`，但事务正常结束，则 A 的业务 SQL 仍会 COMMIT。

因此 Core 故意抛内部 `CompletionRejectedException`：

```text
markSuccess != UPDATED
   ↓
throw
   ↓
Tx-B rollback
   ↓
再转换为 OWNERSHIP_LOST
```

这使 owner/version CAS 不只保护幂等表，还能够在同一个本地事务里阻止 stale owner 的业务 SQL 提交。

---

# 22. ResultPolicy：结果回放到底是什么

结果回放解决的是：

> 历史已经 SUCCESS，本次不再执行业务，但调用方希望拿到什么？

它不是 Retry。

```text
Retry  = 再次执行 Business
Replay = Business 不执行，复用历史成功事实/结果
```

## NONE

默认：

```text
第一次：Business → SUCCESS
第二次：SUCCESS → REPLAYED，value=null
```

适合 MQ、后台任务、只关心“做没做过”的场景。

## SNAPSHOT

第一次：

```text
OrderResult
  ↓ serialize
result_payload
```

第二次：

```text
SUCCESS
  ↓
result_payload
  ↓ deserialize
OrderResult
```

适合 HTTP 短窗口重复请求。

通过 `IdempotencyTypeRef<T>` 支持：

```java
List<OrderResult>
Map<String, OrderResult>
Page<OrderResult>
```

主 Executor API 不再需要 `Class<T>`。

## REFERENCE

长期 DURABLE 场景往往不适合永久保存大 DTO JSON。

可以只保存：

```text
orderId=888
```

重复请求时：

```text
888
  ↓
业务 Query Service
  ↓
重新得到 OrderResult
```

长期稳定业务引用通常比历史 DTO 快照更健康。

---

# 23. 为什么 ResultPolicy.capture 也在 Tx-B 中

如果 Business 成功写数据库，但结果快照序列化失败：

```text
Business 已提交
SUCCESS 没保存
```

又会出现不一致。

因此 Tx-B 是：

```text
Business
+
ResultPolicy.capture
+
markSuccess
```

任一步失败，都让同库业务事务整体 rollback。

---

# 24. StoredResultEnvelope 为什么存在

result_payload 不只是裸 JSON。

V2.1 使用内部 envelope：

```text
IR1|SNAPSHOT|...
IR1|REFERENCE|...
```

它解决两个问题：

1. 重复请求时可以判断历史数据是 SNAPSHOT 还是 REFERENCE；
2. 如果当前调用 ResultPolicy 与历史保存策略不一致，返回 `RESULT_POLICY_MISMATCH`，而不是错误解码。

历史旧版本裸 payload 仍按 legacy SNAPSHOT 兼容。

---

# 25. 业务失败后的 Tx-C

Tx-B 中 Business 抛异常：

```text
Tx-B rollback
```

但 Tx-A 已经提交过 PROCESSING，所以数据库此时仍然是 PROCESSING。

需要把失败事实独立留下：

```text
Tx-C REQUIRES_NEW
  ↓
markFailed(owner, version)
  ↓
COMMIT
```

为什么不能在失败的 Tx-B 中 markFailed？因为它会和 Tx-B 一起 rollback。

`markFailed` 同样使用 owner/version CAS，旧 generation 没资格把新 generation 写成 FAILED。

---

# 26. FailureClassifier 与 FAILED_RETRYABLE

基础组件不能替业务判断所有异常都能重试。

例如：

```text
参数错误
余额不足
权限失败
银行调用结果未知
```

随意重做都可能危险。

所以 FailureClassifier 默认应保守。

记录中保存：

```text
failureCode
failureMessage
failureRetryable
```

Repository 再把 FAILED 判定为：

```text
FAILED_RETRYABLE
FAILED_FINAL
```

但普通 execute() 即使看到 RETRYABLE 也不自动重跑，仍交给显式 Recovery。

---

# 27. Recovery 为什么是一条独立入口

可靠恢复分两步：

```text
扫描候选
    ↓
真正接管
```

扫描只是观察，不等于拥有执行权。

## 扫描

`IdempotencyRecoveryQueryService` 找到：

```text
namespace
key
routeKey
owner=A
version=10
```

外部 Reliable Task 创建恢复任务。

## 真正 recover()

任务执行时必须携带：

```text
expectedOwner=A
expectedVersion=10
```

然后 Repository.tryRecover() 再做一次原子 CAS。

---

# 28. 为什么 Recovery 必须二次 CAS

扫描时：

```text
T1：看到 A/10 已过期
```

任务真正运行前：

```text
T2：C 已经先接管成 C/11
```

T3 旧任务才执行。

如果不重新验证，旧扫描结果会误触发第二次恢复。

因此 tryRecover 检查：

```text
expectedOwner=A
expectedVersion=10
```

当前已经 C/11，则返回：

```text
STALE_CANDIDATE
```

不执行 Business。

只有仍然匹配且 RecoveryPolicy 允许时，才原子更新：

```text
owner=B
version=11
status=PROCESSING
new processingExpireAt
```

返回 `RECOVERY_ACQUIRED`，然后复用同一 executeOwned / Tx-B / Tx-C 主链。

---

# 29. RecoveryPolicy 为什么替代多个 boolean

以前容易出现：

```text
retryOnProcessingTimeout
retryFailed
```

boolean 越加越多，语义越来越散。

现在 `IdempotencyRecoveryPolicy` 集中表达：

```text
mode=NONE / EXTERNAL_TASK
recoverProcessingTimeout
recoverRetryableFailure
```

未来需要增加更细策略时也不会继续污染 Request。

---

# 30. COMMIT_UNKNOWN 为什么绝对不能直接写 FAILED

极端场景：

```text
数据库已经 COMMIT 成功
  ↓
返回成功 ACK 时连接断开
```

应用看见 commit exception，但真实数据库可能已经：

```text
Business = committed
Idempotency = SUCCESS
```

此时不能再 Tx-C 写 FAILED。

transaction-component 将这种结果映射为：

```text
COMMIT_UNKNOWN
```

Idempotency 返回：

```text
TRANSACTION_COMMIT_UNKNOWN
```

后续必须通过查询/对账/Recovery 收敛，而不能直接“失败后重试”。

---

# 31. 非事务 Repository 为什么仍然有价值

Redis WINDOWED 与业务 MySQL 不能被普通本地事务原子提交。

因此 Redis 模式主要依赖：

```text
Lua 状态机
owner/version
业务自身幂等/唯一约束
下游幂等号
```

Core 仍会执行 markSuccess CAS，但不会假装 Redis + MySQL 已经变成一个本地事务。

`RepositoryCapabilities.businessTransactionParticipationSupported` 就是为了避免这种虚假承诺。

---

# 32. 外部副作用不是本地事务能解决的

例如 Tx-B 内调用：

```text
bankClient.deduct()
```

银行已经扣款，然后本地事务 rollback。

银行不会跟着 MySQL rollback。

因此对外部副作用仍需要：

```text
下游幂等号
状态查询
Outbox / 事务消息
Saga / 补偿
对账
```

幂等组件不能承诺跨系统原子性。

  ├─ find candidates

# 35. 各层一句话职责

| 层 | 真正职责 |
|---|---|
| Request | 这一次请求是谁 |
| Policy | 这种业务应该怎么做幂等 |
| Repository CAS/Lua | **当前 generation 到底属于谁** |
| StateMachine | 已经得到原子事实后，下一步 EXECUTE / REPLAY / RETURN |
| DistributedLock | 减少热点抢占竞争 |
| Transaction Integration | 同库 Business + SUCCESS 原子提交 |
| ResultPolicy | 历史 SUCCESS 后，本次重复请求返回什么 |
| RecoveryPolicy | 哪些异常 generation 允许外部任务接管 |
| Reliable Task | 何时扫描、调度和触发 recover |

最重要的一句话：

> **Repository 决定“谁有资格执行”；StateMachine 决定“知道结果后做什么”；Transaction 决定“业务数据和 SUCCESS 能不能一起提交”；Recovery 决定“旧 generation 异常后谁能成为下一代”。**

# 36. 推荐使用方式

## 36.1 消息消费：只要防重

```java
idempotencyExecutor.execute(
        IdempotencyRequest.builder()
                .key(messageId)
                .policyName("message-consume")
                .build(),
        context -> {
            consume(message);
            return null;
        });
```

默认 NONE，不需要保存结果。

## 36.2 HTTP 短窗口 + 返回第一次响应

```java
IdempotencyResultPolicy<OrderResult> snapshot =
        snapshotPolicyFactory.snapshot(
                new IdempotencyTypeRef<OrderResult>() {});

return idempotencyExecutor.execute(
        IdempotencyRequest.builder()
                .key(requestId)
                .requestHash(requestHash)
                .policyName("order-submit-windowed")
                .build(),
        snapshot,
        context -> orderService.submit(command));
```

## 36.3 DURABLE + 稳定业务引用

```java
IdempotencyResultPolicy<OrderResult> reference =
        IdempotencyResultPolicies.reference(
                new IdempotencyResultReference<>() {
                    public String capture(OrderResult value) {
                        return value.orderId();
                    }
                    public OrderResult resolve(String orderId) {
                        return orderQueryService.find(orderId);
                    }
                });
```

长期幂等记录只保存稳定 orderId，而不是长期保存 DTO JSON。

# 37. 当前设计最重要的边界

这套组件能保证的是：

```text
同一幂等 key 的状态正确性
合法 generation 管理
重复请求不重复成为合法执行者
旧 owner 无权完成新 generation
同库事务场景 Business + SUCCESS 原子提交
显式安全 Recovery
```

它不能单独保证：

```text
外部银行接口不重复扣款
不同数据库之间原子提交
消息与数据库天然同事务
任何旧 Java 线程物理停止
```

这些必须依赖业务唯一约束、下游幂等、事务消息、补偿和对账共同完成。

---

# 38. 最终心智模型

不要把整个组件记成“一锁二查三判断”。

更准确的心智模型是：

```text
稳定识别逻辑请求
        ↓
Repository 原子授予 execution generation
        ↓
StateMachine 决定执行 / 回放 / 返回
        ↓
合法 owner 执行业务
        ↓
owner + version 条件完成最终状态
        ↓
同库时 Transaction 保证 Business + SUCCESS 原子性
        ↓
历史 SUCCESS 只 Result Replay，不重新执行业务
        ↓
异常 generation 只能由显式 Recovery 二次 CAS 接管
```

如果这条链理解清楚，WINDOWED、DURABLE、Lock、Transaction、ResultPolicy、Recovery 就不会再串不起来。
