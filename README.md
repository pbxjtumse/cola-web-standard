# 2. 建设背景

当前工程基于 COLA 分层架构进行组织，整体包含：

* `adapter`
* `app`
* `client`
* `domain`
* `infrastructure`
* `start`
* `component`

其中：

* `adapter / app / domain / infrastructure / start` 负责业务应用分层；
* `component` 负责技术组件、基础设施能力和可复用底座能力沉淀。

随着项目逐步演进，当前已经形成或正在形成以下技术能力：

* Foundation 基础能力组件
* 缓存组件
* 并发 / 并行执行组件
* 消息组件
* 重试组件
* 分布式锁组件
* 治理组件
* 可观测性组件
* 事务增强组件
* 后续幂等、Outbox、一致性补偿组件

当前项目已经不再是简单业务工程，而是在逐步演进为：

> 业务应用 + 技术组件底座 + 工程治理规范

三层并行推进的技术体系。

当前仍然存在以下问题：

1. 部分技术组件已有设计和代码，但尚未全部完成真实业务接入；
2. Foundation 能力已经形成，但还需要逐步替换各组件内部重复基础代码；
3. Maven 父子继承、BOM、依赖管理曾存在历史混乱，目前已经开始规范化；
4. 可观测性指标标准已经明确，但各组件尚未全部接入 Prometheus / Grafana；
5. 单元测试、集成测试、压测体系仍需系统补齐；
6. 部分 Starter、Provider、Integration 依赖边界还需要继续收敛；
7. 文档、代码、Demo、压测报告之间仍需建立长期同步机制。

因此，当前阶段核心目标为：

**在保留现有 COLA 主体分层结构的前提下，对技术组件体系进行系统化整理、分阶段重构、测试验证和观测接入。**

# 3. 总体建设目标

技术组件体系的长期目标如下。

## 3.1 统一基础能力

将 ID、时间、上下文、序列化、编解码、反射、资源读取、参数校验、异常辅助、通用集合 / 字符串工具等稳定能力沉淀到 Foundation Component，避免各组件重复实现基础能力。

Foundation 的目标不是重新发明一个大而全工具库，而是：

* 优先复用 JDK 和成熟开源组件；
* 在项目内部提供统一、薄、稳定的使用门面；
* 避免工具类和业务语义混杂；
* 为消息、重试、缓存、锁、并发、幂等等组件提供底层支撑。

## 3.2 统一组件边界

每个技术组件必须明确：

* 负责什么；
* 不负责什么；
* 对外暴露哪些 API；
* 哪些是内部实现；
* 依赖哪些基础组件；
* 不允许反向依赖哪些上层组件。

典型原则：

* Retry 只负责“是否再次执行”，不负责业务幂等和补偿；
* Message 负责消息发送、消费、ACK、失败处理，不负责业务幂等规则；
* Lock 负责互斥控制，不替代事务、幂等和一致性；
* Cache 负责缓存访问和多级缓存策略，不负责数据库查询优化本身；
* Foundation 不承载任何业务语义，也不依赖任何上层技术组件。

## 3.3 统一使用方式

每一个组件最终都应具备统一的：

* 配置方式；
* 接入方式；
* 扩展方式；
* 监控方式；
* Starter 装配方式；
* Demo 使用方式；
* 故障处理方式。

## 3.4 统一治理能力

所有技术组件最终都需要纳入统一治理体系，包括：

* 日志；
* 指标；
* Trace / 上下文透传；
* 异常观测；
* 告警接入；
* 性能与容量分析；
* 压测数据沉淀。

## 3.5 保持实现可替换

技术组件不应与单一实现强绑定。

例如：

* 消息组件不绑定 Kafka / RocketMQ / Pulsar 中某一个；
* 分布式锁组件不绑定 Redis 单一实现；
* 序列化不在公开 API 层绑定 Jackson；
* 缓存组件不绑定单一 Caffeine 或 Redis；
* 可观测性不绑定单一 APM 平台；
* 幂等组件不绑定单一入口场景。

## 3.6 面向后续技术中台建设

本组件体系不仅服务当前项目，还将作为后续技术中台、业务平台、复杂业务系统、AI Agent 项目和个人技术体系建设的公共底座。

# 5. 架构原则

## 5.1 业务与技术组件解耦

技术组件不依赖具体业务模型，不承载业务语义，不将业务逻辑沉淀到基础组件内部。

## 5.2 Foundation 只能被依赖，不能反向依赖上层组件

    ↓
技术组件
    ↓
Foundation
    ↓
JDK / 开源基础库
